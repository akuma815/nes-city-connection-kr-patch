# 결정 기록 / 한글화 가능 여부 판단

## D-001. 한글화 가능 여부 — **가능하다 (난이도 낮음)**

2026-08-12 정적 조사 + 실행 검증 결과다. 근거는 `docs/survey.md`.

### 가능하다고 보는 이유

| 항목 | 상태 |
| --- | --- |
| 텍스트 압축 | 없음 |
| 포인터 테이블 | 없음 (코드 안 절대 참조) |
| 문자 인코딩 | 없음. 바이트 = 타일 번호, 배치가 ASCII |
| 텍스트 총량 | 문자열 8덩이, **168바이트** |
| 일본어 글리프 | **없음.** 일본판인데 화면 문자가 전부 영문·숫자다 |
| 폰트 위치 | CHR-ROM에 그대로 노출, 압축 없음 |
| 렌더러 | 고정폭 8×8, 1글자 = 1타일. 한글도 같은 규칙으로 그대로 나온다 |
| 필요한 6502 코드 수정 | **0** |

가변폭 폰트, 조합형 조판, 포인터 재계산, 압축 재구현이 하나도 필요 없다.
**타일 그림을 한글 글리프로 바꾸고 문자열 바이트를 새 타일 번호로 바꾸면 끝난다.**

2026-08-12 실행 검증에서 `READY` → `준비` 최소 PoC가 실제 화면에 정상 표시됐다(D-003).

### 유일한 제약: 타일 예산 — 실측으로 확정

`analyze_tile_usage.py`가 원본 ROM 실행 40,000프레임의 네임테이블 사용량과
`rom_map.json`의 원문 실바이트를 대조해 판정한 결과다.

| 구분 | 슬롯 수 | 내용 |
| --- | ---: | --- |
| 원문 문자열 전용 | 27 | `2D 2E 2F 41-45 47-50 52-57 59 5D 5F` — 번역하면 그대로 빈다 |
| 카나리아 전 도시 검증 | 11 | `28-2C 46 51 58 5A 5B 5E` — 6개 도시 어디에도 안 나타남 |
| **확정 회수 가능 합계** | **38** | |
| 회수 금지 | — | `30-39` 숫자, `3A-3F` 배경·게이지·**하늘**, `40` 공백, `5C` 카운트다운 소수점 |

**한글 글리프 예산: 확정 38자.** 필요한 27자 대비 여유 11자.

### 예산이 충분한지

필요한 서로 다른 음절을 실제 문구로 세면 다음과 같다.

| 원문 | 번역안 | 새 음절 |
| --- | --- | ---: |
| `1PLAYER` / `2PLAYERS` | `1인용` / `2인용` | 인 용 = 2 |
| `GAME OVER` | `게임오버` | 게 임 오 버 = 4 |
| `READY` | `준비` | 준 비 = 2 |
| `WARP BONUS` | `워프보너스` | 워 프 보 너 스 = 5 |
| `OIL.1000POINT` | `기름.1000점` | 기 름 점 = 3 |
| `OIL`(HUD) | `기름` | 0 (중복) |
| `TOP` | `최고` | 최 고 = 2 |
| 엔딩 2줄 | `모든 고속도로를 달렸다!!` | 모 든 속 도 로 를 달 렸 다 = 9 |
| **합계** | | **27** |

**확정 38슬롯에 여유 11자를 남기고 들어간다.** `JALECO`, `1P`, `2P`, `KM`, `UP`을 원문 그대로 두면
그 영문 슬롯은 한글에 못 쓰지만(남긴 영문 1자 = 한글 1자 감소), 여유가 있어 문제되지 않는다.

### 새로 드러난 제약: 타이틀 메뉴는 한 줄 8타일

타이틀 메뉴 문자는 BG가 아니라 **스프라이트**이고, 각 줄이 정확히 8개다(`docs/survey.md` 2장).
NES는 스캔라인당 스프라이트 8개가 한계이므로 **번역문도 한 줄 8타일을 넘길 수 없다.**
`1인용`(3), `2인용`(3)은 여유가 크다.

### 예산이 모자랄 때의 확장 경로

1. **문구 단축** — 가장 싸다. NES 한글화의 정석이다.
2. **미관측 후보 11슬롯 회수** — 커버리지를 넓혀 재확인한 뒤 사용한다(D-004).
3. **CHR-ROM 32KB 확장** — 매퍼 87의 뱅크 레지스터는 2비트라 8KB 뱅크 4개까지 지원한다.
   `$6000` 스토어 4곳과 뱅크 변수 `$67`을 고쳐야 하고 **PRG 자유 공간이 약 61바이트뿐**이라 마지막 수단이다.
   참고로 `H:\Mesen\Debugger\City Connection (Korea Natural Expanded).cdl`은 PRG 16KB + **CHR 32KB** 구성의
   기록이므로, 이 확장 자체는 실제로 가능한 경로다. 다만 남의 결과를 근거로 삼지 않고 필요할 때 직접 증명한다.

### 판단하지 않은 것

- 타이틀 로고 `CONNECTION`(PT0 뱅크0, 21×6타일)을 한글로 바꿀지. 폰트 예산과 완전히 별개 영역이라
  기술적으로는 자유롭게 다시 그릴 수 있다. 로고 원문 유지 여부는 사용자 결정 사항이다.
- 미국판·유럽판 대응.

## D-002. 8×8 한글 폰트 — Galmuri8x8

`Font/Galmuri8x8.ttf`를 **16ppem**으로 열면 잉크가 정확히 8×8이다(이 폰트는 16ppem 스트라이크만 열린다).
후보 비교 결과 안티앨리어싱이 없는 순수 1비트라 임계값 없이 그대로 쓸 수 있고, 표본 38자가 전부 8×8에 들어갔다.

- 글자별로 잉크를 중앙 정렬하면 기준선이 흔들린다. `make_glyphs.py`는 표본 전체의 잉크 경계를 한 번 재서
  **전 글자 공통 원점**(4, 4)을 잡고 그 원점으로만 그린다.
- 픽셀은 색 0과 색 3만 쓴다. 원본 영문 폰트도 색 3 한 가지라 팔레트를 건드리지 않아도 된다.
- Galmuri8x8은 완성형 부분집합이라 없는 음절이 있다(예: `힣`). 번역문 확정 시 `--coverage`로 검사한다.

라이선스는 배포 직전에 다시 확인한다. 배포물에는 TTF가 아니라 **파생 비트맵만 ROM 안에** 들어간다.

## D-003. 최소 PoC — **통과 (2026-08-12)**

가이드 3단계 원칙대로 전체 폰트를 굽기 전에 최소 PoC부터 통과시켰다.

1. **무변경 왕복 — PASS.** `build_rom.py --verify`가 원본과 바이트 동일(SHA 일치)을 확인했다.
2. **`READY`(6타일) → `준비` — PASS.** 다른 문자열이 전혀 쓰지 않는 `F`(`0x46`)/`Q`(`0x51`) 슬롯만 회수해
   글리프 2개를 굽고, 문자열을 `40 40 46 51 40 40`으로 길이 그대로 치환했다.
   Mesen 헤드리스 실행 프레임 620~660에서 화면에 `준비`가 정상 표시됐다(`work/qa/ready/zoom_ready.png`).
3. **Expected Write — PASS.** 선언한 오프셋 밖 변경 0바이트.

이로써 "타일 교체 + 문자열 바이트 교체"만으로 한글이 화면에 나온다는 것이 증명됐다.

## D-004. 빈 타일 회수 — **`0x3F`는 회수 금지로 확정**

1차 정적 조사에서 `0x28-0x2C`와 `0x3F`를 "ROM에서 비어 있으니 회수 후보"로 적었다. **`0x3F`는 틀렸다.**

- 네임테이블 집계: `0x3F`가 **310,866회** 참조됐다.
- 카나리아 빌드(`patch_canary.json`)로 `0x3F`에 체커보드를 넣자 **하늘 전체가 체커보드로 바뀌었다.**

`0x3A`, `0x3B`, `0x3D`, `0x3E`, `0x40`도 같은 이유로 회수 금지다.

**원칙: ROM에서 비어 있다는 사실만으로 자유 슬롯으로 간주하지 않는다.** 이 프로젝트에서 실제로 한 번 틀렸다.

### 후보 11슬롯 — 전 도시 검증 완료 (2026-08-12)

스테이지 변수 `$A0`을 찾아(D-007) 6개 도시를 전부 로드한 뒤 다시 검사했다.

- `patch_canary_blank.json`에 후보 11슬롯(`28-2C 46 51 58 5A 5B 5E`)을 모두 넣고
  각 도시 3,000프레임씩 실행, 스크린샷 18장에서 **체커보드 미출현**(`work/qa/canary_all_stages.png`).
- 같은 6개 도시를 원본 ROM으로 돌린 네임테이블 집계에서도 11슬롯 전부 **PT1 사용 0회**.
- CHR 뱅크 0·1 모두 관측했다(스테이지 2·4·5가 뱅크 1).

**따라서 회수 가능 슬롯은 38개로 확정한다.** 근거는 `rom_map.json`의 `glyph_budget.canary_evidence`에 있고,
`analyze_tile_usage.py`가 그 목록을 읽어 판정에 반영한다.

남은 미검증 화면은 엔딩뿐이며, 엔딩이 쓰는 타일은 전부 원문 문자열 안에 있어 예산에 영향이 없다.

## D-005. QA는 Mesen 헤드리스 테스트 러너로 자동화한다

Mesen 2는 GUI 앱이지만 숨은 옵션이 있다.

```
--testRunner [lua script] [rom file]   헤드리스로 Lua 스크립트 실행
--enableStdout                         로그 창 내용을 stdout으로
```

- 종료는 도움말에 적힌 `emu.exit()`이 **아니라** `emu.stop(0)`이다(이 빌드의 API에 `exit`가 없다).
- `emu.getState()`는 중첩 테이블이 아니라 `"ppu.mask.backgroundEnabled"` 같은 **평면 키**를 준다.
- 명령행에 `.lua`를 그냥 넘기면(테스트 러너 없이) 스크립트는 실행되지 않는다.
- 스크립트가 파일을 쓰려면 Mesen 설정의 `Debug > ScriptWindow > AllowIoOsAccess`가 `true`여야 한다.
  이 프로젝트를 위해 켰고, 원본은 `H:\Mesen\settings.json.bak-korproj`에 백업해 뒀다.
- PowerShell 5.1의 `Start-Process -ArgumentList`는 공백 있는 경로를 자동으로 따옴표로 감싸지 않는다.
  `run_qa.py`는 ROM을 공백 없는 출력 폴더로 복사한 뒤 실행한다.

20,000프레임 실행이 약 34초다. 스크린샷·네임테이블 집계·CDL 덤프를 한 번에 얻을 수 있어
타일 회수 판정과 번역 결과 확인을 모두 자동으로 돌린다.

## D-009. 번역 문구 — 슬롯 예산이 문안을 결정한다

전량 번역은 `workspace/text/translation/translation.json` 하나에서 나온다.
`build_translation.py`가 슬롯을 배정하고 예산·길이·폰트 커버리지를 검사한다.

### 회계

| 항목 | 슬롯 |
| --- | ---: |
| 회수 가능(D-004) | 38 |
| 원문 유지 글자가 예약 | 15 (`✳ A C E J K L M O P R T U Y` + HUD 기호) |
| **한글에 쓸 수 있는 슬롯** | **23** |
| 실제 사용 음절 | 23 (여유 0) |

**원문 영문 1자를 남길 때마다 한글 1자를 못 쓴다.** 첫 빌드에서 이 예약을 빼먹어
`JALECO`가 한글로 덮여 깨졌다. 지금은 도구가 예약을 먼저 하고 남는 슬롯에만 배정한다.

### 원문을 유지한 것과 그 이유

| 대상 | 이유 |
| --- | --- |
| `JALECO`, `© 1985` | 제작사·저작권 표기 |
| `UP` (HUD) | 정적 라벨이 **3칸**뿐이라 `플레이어`(4칸)가 안 들어간다. 사용자 지시대로 원문 유지 |
| `KM` | 단위. 한글로 바꿀 실익이 없고 슬롯만 더 든다 |
| `1P` / `TOP` / `2P` | `최고`로 바꿔도 슬롯 이득이 없다(`T` 하나 절약, `최`·`고` 두 자 소모) |
| ` PLAYER` (`$8B48`) | 같은 7바이트를 **간주 화면과 게임오버 화면**이 쓰는데 플레이어 번호가 앞뒤로 갈린다. 한글 단어를 넣으면 한쪽이 반드시 어색해진다 |

### 줄인 것

엔딩 원문 `NOW,YOU HAVE DRIVEN / ALL THE HIGHWAY!!`에 가까운
`이제 모든 고속도로를 / 달렸습니다!!`는 6자를 더 먹어 들어가지 않는다.
`이제 모두 / 달렸다`로 줄였고, `!!`(1슬롯)와 `=`(1슬롯)도 뺐다.

### 이 단계에서 배운 것

1. **정적 조사만으로는 화면 문자열을 다 못 찾는다.** ` PLAYER`는 QA 스윕에서
   `1 PLA인용`으로 깨진 화면을 보고서야 찾았다. 그래서 `audit_strings.py`를 만들어
   PPUDATA에 쓰는 모든 루프를 원장과 대조하게 했다.
2. **길이가 같아도 표시 칸은 다르다.** HUD는 30바이트지만 동적 필드가 덮어써
   실제로 쓸 수 있는 칸은 3개다. 네임테이블 덤프와 그리기 코드를 둘 다 봐야 한다.
3. **한 문자열을 두 화면이 공유할 수 있다.** 번역 가능 여부는 문자열 단위가 아니라
   **모든 사용처의 배치**를 보고 판단해야 한다.

## D-008. 타이틀 로고를 `시티 커넥션`으로 다시 그린다

원본은 작은 필기체 `City` 위에 큰 `CONNECTION`이 있는 21×6 타일 그림이다.
`$8A3D` 루틴이 `$8D94`부터 읽어 PPUADDR `$2105`(8행 5열)에 쓰고, `0xFE`마다 다음 행의 같은 열로 간다.

### 제약 — 모두 실측

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 데이터 길이 | **118바이트 고정** (`$8D94`~`$8E09`) | 그 뒤 `$8E0A`가 엔딩 문구다 |
| 화면 위치 | 8행 5열 시작, 행마다 +32 | `$8A3D` 루틴 |
| 쓸 수 있는 타일 | **32종** | `analyze_logo.py` |
| 색 | 본체 값 2(분홍), 그림자 값 3(살구), 하이라이트 값 1(흰) | 원본 로고 타일의 픽셀 값 분포 |

로고는 PT0을 쓰고 타이틀 화면은 CHR 뱅크 0이므로 **뱅크 0의 PT0만** 고친다.

### 타일 32종은 어떻게 나왔나

- 로고 전용 타일 31종: 로고 타일맵이 쓰는 34종에서 `0x40`(빈 타일, 스프라이트도 씀),
  `0x50`(게임 스프라이트 234회), `0x60`(앞 루틴의 RTS라 애초에 로고 데이터가 아님)을 뺀 값.
- `0x3E` 1종: 어디에서도 안 쓰이고 CHR에서도 완전히 비어 있다.

관측만으로 "안 쓰인다"고 판단하지 않았다. 미관측 인덱스 90종을 CHR 실바이트와 대조하니
**89종에 그림이 들어 있었다**(사망 연출·보너스·`PAUSE` 등 이번 실행에서 안 나온 것들).
그래서 미관측이면서 CHR도 빈 `0x3E` 하나만 추가했다.

### 32종 안에 넣는 방법

1. **음절을 타일 격자에 정렬한다.** 자유 배치보다 같은 8×8 조각이 겹칠 확률이 높다.
2. **거의 같은 타일을 병합한다.** 예산을 넘으면 픽셀 차이가 가장 적은 쌍부터 합친다.
   글자를 다시 디자인하는 대신 픽셀 몇 개를 양보하는 방식이다.
3. **그림자와 테두리는 거의 공짜다.** 본체를 1px 밀어 값 3 그림자를 깔거나 둘레에 1px 테두리를
   둘러도 유니크 타일이 거의 늘지 않는다(24px 기준 단색 38 → 그림자+테두리 39).
   같은 모양을 옮기거나 부풀린 것이라 타일 *종류*가 늘지 않기 때문이다.
   반면 글자를 키우면 바로 는다(20px 37 → 24px 39).

### 흰 테두리는 장식이 아니라 가독성 장치다

본체만 분홍으로 칠하면 붙어 있는 음절끼리 덩어리로 보인다.
둘레에 값 1(흰) 1px 테두리를 두르면 음절 경계가 갈라져 읽힌다. 비용은 사실상 0이다.
원본 로고도 같은 구성이다(살구 외곽 + 분홍 본체 + 흰 하이라이트).

### 현재 채택안

`RixInooAriDuri Regular` **22px**, 3×3타일 칸, `시티`(7열 0행) / `커넥션`(6열 3행),
본체 값 2(분홍) + 흰 테두리 1px + 살구 그림자 1px.
유니크 37→32(병합 5), 데이터 90/118바이트. `build/logo_kr.nes`에서 화면 확인 완료.

24px도 들어가지만(병합 7) 음절이 서로 붙고 `션` 아래쪽이 뭉개져 22px를 골랐다.

  --grid "시티:7:0,커넥션:6:3" --cell-w 3 --cell-h 3 --color 2 --shadow 1 --outline 1 --emit

더 키우려면 CHR을 32KB로 확장해야 하는데(D-001의 3번), 로고 하나 때문에 갈 만한 길은 아니다.

## D-007. 커버리지는 실력이 아니라 상태 변수로 넓힌다

자동 입력으로는 1스테이지를 벗어날 수 없어 뒤 도시의 배경 타일을 볼 수 없었다.
스테이지를 클리어하는 대신 **스테이지 인덱스 변수를 강제로 쓰는 방법**을 택했다.

찾은 경로는 `$A2DA`의 `LDX $A0 : LDA $A2B6,X : STA $6000`이다.
`$A0`이 스테이지 인덱스(0~5), `$A2B6`이 스테이지→CHR 뱅크 표다(`docs/survey.md` 6장).

`$A0`은 세 곳에서만 쓰이고 나머지는 전부 읽기라 스크래치가 아닌 상태 변수다.
`run_qa.py --poke A0=N`이 **프레임 경계에서만** 쓰므로 프레임 중간 로직을 건드리지 않는다.

이 방식으로 6개 도시를 각각 3,000프레임씩 돌려 D-004를 닫았다. 사람 플레이 없이 끝났다.

원칙: **관측 범위가 부족하면 플레이 실력을 올리려 하지 말고 그 범위를 결정하는 변수를 찾는다.**

## D-006. 판정 근거는 전사가 아니라 원본 바이트에서 읽는다

`analyze_tile_usage.py`의 첫 버전은 `rom_map.json`의 `text` 전사 문자열로 사용 문자를 계산했다.
그 결과 HUD 끝의 `0x5F`와 보너스 문구의 `0x2E`를 놓쳐 "배경이 쓰는 타일"로 잘못 분류했다.

지금은 `addr + length`로 `extracted/prg.bin`을 직접 읽는다. 전사는 사람이 읽기 위한 주석일 뿐이다.

또한 PT0와 PT1은 서로 다른 CHR 4KB 영역이므로 **같은 타일 인덱스라도 서로 무관하다.**
첫 버전은 이걸 섞어서 "타이틀에서 쓰이니 회수 불가"라는 잘못된 판정을 냈다.
